# SplitBill

แอปบันทึกค่าใช้จ่ายร่วมกันของกลุ่ม (เช่น ค่าอาหารมื้อค่ำ ค่าห้องพัก) และคำนวณยอดคงเหลือสุทธิของสมาชิกแต่ละคน
แม่นยำระดับสตางค์ ทำเป็นงาน take-home test ของ Chowpa

- **Backend:** Python + FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16
- **Frontend:** Next.js (App Router) + TypeScript + Tailwind CSS
- **เอกสารที่เกี่ยวข้อง:** [AI_NOTES.md](AI_NOTES.md) (การใช้เครื่องมือ AI)

## สิ่งที่ต้องมีในเครื่อง

## API

ทุกคำขอต้องมีเฮดเดอร์ `X-User`

| เมธอด | พาธ | คำอธิบาย |
|---|---|---|
| GET | `/groups` | กลุ่มของผู้ใช้ที่ส่งคำขอ |
| GET | `/groups/{id}` | ข้อมูลกลุ่มพร้อมรายชื่อสมาชิก |
| POST | `/groups/{id}/expenses` | บันทึกค่าใช้จ่าย (ส่ง `Idempotency-Key` ได้) |
| GET | `/groups/{id}/expenses` | รายการค่าใช้จ่าย เรียงใหม่ไปเก่า (ไม่รวมที่ลบแล้ว) |
| DELETE | `/groups/{id}/expenses/{expense_id}` | ลบแบบ soft delete (เฉพาะผู้จ่าย) |
| GET | `/groups/{id}/balances` | ยอดคงเหลือสุทธิ ค่าบวก = กลุ่มเป็นหนี้สมาชิกคนนั้น |

ข้อผิดพลาดทั้งหมดอยู่ในรูปแบบเดียวกัน:

```json
{ "error": { "code": "invalid_request", "message": "The shares add up to 90.00 but the amount is 100.00" } }
```

| สถานะ | `code` | เมื่อไร |
|---|---|---|
| 401 | `unauthorized` | ไม่มี `X-User` หรือไม่รู้จักผู้ใช้ |
| 403 | `forbidden` | สมาชิกที่ไม่ใช่ผู้จ่ายพยายามลบค่าใช้จ่าย |
| 404 | `not_found` | ไม่พบกลุ่ม/ค่าใช้จ่าย หรือไม่ใช่สมาชิกของกลุ่ม |
| 422 | `invalid_request`, `validation_error` | จำนวนเงินผิดกฎ, ส่วนแบ่งไม่ลงตัว, ผู้จ่าย/สมาชิกไม่อยู่ในกลุ่ม, ข้อมูลไม่ครบ |

## การตัดสินใจเชิงออกแบบและเหตุผล

### 1. คนนอกกลุ่มได้ 404 ไม่ใช่ 403

คำขอจากผู้ที่ไม่ใช่สมาชิกกลุ่ม (เช่น alice เข้ากลุ่ม 2) ตอบ **404 "Group not found"** เหมือนกับกรณีที่กลุ่มไม่มีอยู่จริง

- **เหตุผล:** 403 บอกคนนอกว่า "กลุ่มนี้มีอยู่ แต่คุณเข้าไม่ได้" ซึ่งเป็นข้อมูลรั่ว 404 ทำให้แยกไม่ได้ระหว่างกลุ่มที่ไม่มีกับกลุ่มที่ไม่มีสิทธิ์
- **ข้อเสีย:** ดีบั๊กยากขึ้นเล็กน้อย เพราะผู้ใช้เห็นแค่ "ไม่พบ" ในกรณีที่แท้จริงคือไม่มีสิทธิ์
- **ข้อยกเว้นที่ตั้งใจ:** สมาชิกของกลุ่มที่พยายามลบค่าใช้จ่ายของคนอื่นได้ **403** เพราะเขาเป็นสมาชิกอยู่แล้ว
  ย่อมเห็นรายการนั้นได้ จึงไม่มีอะไรต้องซ่อน และข้อความ "Only the payer can delete this expense" มีประโยชน์กว่า
- ใช้กับทุก endpoint ภายใต้ `/groups/{id}` (อ่านและเขียน) และมีเทสต์ยืนยันว่า alice อ่าน/เขียนกลุ่ม 2 ไม่ได้ และไม่มีอะไรถูกบันทึก

### 2. การเก็บเงิน: ไม่มี float ที่ใดเลย

- ฐานข้อมูล: `NUMERIC(12,2)` พร้อม `CHECK (amount > 0)` ที่ค่าใช้จ่าย และ `CHECK (amount >= 0)` ที่ส่วนแบ่ง
- Python: `Decimal` ทั้งหมด จำนวนเงินเดินทางใน JSON เป็นสตริง (`"1000.00"`) ทั้งขาเข้าและขาออก
- `parse_amount` ปฏิเสธ: ไม่ใช่สตริง, ไม่ใช่ตัวเลข (รวม `NaN`/`Infinity`), ศูนย์หรือติดลบ, ทศนิยมเกิน 2 ตำแหน่ง
  (`"10.005"`) และเกิน 9,999,999,999.99 (ขีดจำกัดของ `NUMERIC(12,2)`)
- ฝั่ง frontend ใช้จำนวนเต็มสตางค์ (ดูหัวข้อด้านล่าง)

### 3. การแจกสตางค์ที่เหลือ

คิดเป็นจำนวนเต็มสตางค์ แล้ว `divmod(total, จำนวนคน)` ทุกคนได้ผลหารเท่ากัน และ **คนที่อยู่ลำดับต้นๆ ตามที่ระบุในคำขอ**
ได้เพิ่มคนละ 1 สตางค์จนเศษหมด ตัวอย่าง 100.00 ÷ 3 = 33.34, 33.33, 33.33 ผลรวมเท่ายอดเสมอ

- ลำดับ = ลำดับของ `members` ในคำขอ (ไม่ใช่ลำดับตัวอักษร) รายชื่อซ้ำถูกปฏิเสธ
- การแบ่งแบบ exact ต้องรวมกันเท่ายอดทุกสตางค์ ไม่เช่นนั้นปฏิเสธพร้อมข้อความ
  `The shares add up to X but the amount is Y`

### 4. ยอดคงเหลือรวมเป็นศูนย์เสมอ

ยอดคงเหลือของสมาชิก = (ผลรวมที่จ่าย) − (ผลรวมส่วนแบ่งของตนเอง) คำนวณด้วย `SUM` ใน SQL จากค่าใช้จ่ายที่ยังไม่ถูกลบ
เนื่องจากทุกรายการถูกบังคับให้ผลรวมส่วนแบ่ง = ยอดค่าใช้จ่ายก่อนบันทึก และผู้จ่าย/ผู้แบ่งทุกคนเป็นสมาชิกกลุ่ม
ผลรวมยอดคงเหลือทุกคนจึงเป็น 0.00 พอดี API คืนช่อง `total` ไว้ให้ตรวจ และมีเทสต์ยืนยัน

### 5. Idempotency (รวมกรณีคำขอพร้อมกัน)

- ฐานข้อมูลมี `UNIQUE (group_id, idempotency_key)` เป็นตัวตัดสินสุดท้าย
- ขั้นตอน: ถ้ามี key อยู่แล้วในกลุ่มนี้ → คืนรายการเดิม (HTTP 200 แทน 201) โดยไม่สร้างใหม่
  ถ้าไม่มี → บันทึก ถ้าคำขอสองอันผ่านการเช็กพร้อมกัน ฝั่งที่แพ้จะชน unique constraint
  แล้วระบบ rollback และดึงรายการของฝั่งที่ชนะมาคืน
- **ทำไมไม่เช็กใน Python อย่างเดียว:** มีช่องว่างระหว่าง "เช็ก" กับ "บันทึก" ให้คำขอพร้อมกันลอดเข้ามา
  ฐานข้อมูลเป็นจุดเดียวที่ตัดสินได้เด็ดขาด
- เทสต์ `test_idempotency_key_holds_for_concurrent_requests` ส่ง 8 คำขอพร้อมกัน ต้องได้รายการเดียว
  และมีเพียงคำขอเดียวที่ตอบ 201
- key เดียวกันใน **คนละกลุ่ม** ถือเป็นคนละรายการ (โจทย์ระบุ "ในกลุ่มเดียวกัน")

### 6. ลบแบบ soft delete และห้ามแก้ไข

ไม่มี endpoint แก้ไขค่าใช้จ่าย การลบตั้ง `is_deleted = true` และ `deleted_at` แถวยังอยู่ในฐานข้อมูล
แต่ไม่ปรากฏในรายการและไม่นับในยอดคงเหลือ เฉพาะผู้จ่ายลบได้

### 7. โครงสร้างโค้ดแยกชั้น (OOP)

`routers` (รับ-ส่ง HTTP) → `services` (กฎธุรกิจ) → `repositories` (SQL) ชั้นบนเรียกชั้นล่างเท่านั้น

- วิธีแบ่งเงินใช้ **Strategy pattern**: `SplitStrategy` (คลาสนามธรรม) กับ `EqualSplit` และ `ExactSplit`
  เพิ่มวิธีแบ่งแบบใหม่ได้โดยไม่แก้โค้ดเดิม
- ข้อผิดพลาดเป็นคลาสสืบทอดจาก `AppError` (มี status code และ code ในตัว) ตัวจัดการเดียวใน `main.py` แปลงเป็น JSON รูปแบบเดียวกัน
- `parse_amount` เป็นฟังก์ชัน ไม่ใช่คลาส เพราะไม่มีสถานะที่ต้องจำ

### 8. Schema, migration และ seed

ตารางจัดการด้วย Alembic เท่านั้น (ไม่มี `create_all`) migration ที่สองใส่ผู้ใช้และกลุ่มตามโจทย์ด้วย id คงที่
และเลื่อนตัวนับ id ของ PostgreSQL ให้ต่อจากค่าที่ใส่เอง `pytest` สร้างฐานข้อมูลทดสอบจาก migration จริง
จึงทดสอบ schema เดียวกับที่ผู้ใช้จริงได้

## แนวทางฝั่ง frontend: ตัวอย่างต้องตรงกับ backend และไม่มี floating-point

`0.1 + 0.2` ใน JavaScript ได้ `0.30000000000000004` จึงไม่ใช้เลขทศนิยมกับเงินเลย

- **จำนวนเต็มสตางค์:** `parseMoney("1000.50")` อ่านข้อความด้วย regex แล้วคิดเป็น `100050` สตางค์
  (ปฏิเสธทศนิยมเกิน 2 ตำแหน่ง ศูนย์ ติดลบ และเกินขีดจำกัด เหมือน backend) การบวกลบหารทำกับจำนวนเต็มทั้งหมด
- **การแบ่งเท่ากัน:** `splitEqual` ใช้อัลกอริทึมเดียวกับ backend (ผลหาร + เศษแจกให้คนแรกๆ ทีละ 1 สตางค์)
  ฟอร์มส่งและแสดงรายชื่อ **ตามลำดับสมาชิกของกลุ่ม** เสมอ ผลที่เห็นในตัวอย่างจึงตรงกับที่ backend บันทึก
  (100.00 ÷ 3 แสดง 33.34 / 33.33 / 33.33)
- **แสดงผล:** `formatMoney` จัดรูปแบบแบบไทย `1,000.00` (ใช้ `Intl.NumberFormat("th-TH-u-nu-latn")` ให้คั่นหลักพันแบบไทยแต่ใช้ตัวเลขอารบิก)
  จำนวนเงินที่ backend ส่งมาถูกอ่านกลับเป็นสตางค์ด้วย `satangFromApi` ไม่ผ่าน `Number`/`parseFloat`
- **ตัวอย่างสดและปุ่มส่ง:** ตรรกะทั้งหมดอยู่ใน `src/lib/split.ts` เป็นฟังก์ชันล้วนๆ ทดสอบได้โดยไม่ต้องเปิดหน้าเว็บ
  แบบ exact แสดง "Unallocated" และปิดปุ่มส่งจนกว่าผลรวมส่วนแบ่ง = ยอดทั้งหมด
- **ข้อผิดพลาด:** `errors.ts` แปลข้อความจาก API เป็นภาษาที่เข้าใจง่าย เช่น "The shares do not add up to the total",
  "Not a member of this group" และกรณี backend ไม่ตอบจะขึ้น "Cannot reach the server. Is the backend running?"
- **Idempotency ฝั่งหน้าเว็บ:** ฟอร์มสร้าง `Idempotency-Key` หนึ่งค่าต่อหนึ่งความพยายามส่ง ถ้าเน็ตหลุดแล้วกดส่งซ้ำ
  จะใช้ key เดิม (backend จึงไม่บันทึกซ้ำ) และสร้างค่าใหม่เมื่อมีการแก้ฟอร์ม
- ปุ่ม Delete แสดงเฉพาะรายการที่ผู้ใช้ปัจจุบันเป็นผู้จ่าย เพื่อความสะดวกเท่านั้น
  ตัวบังคับกฎจริงคือ backend (คนอื่นลบได้ 403)

## ข้อสมมติ (จุดที่โจทย์ไม่ได้ระบุชัด และการตีความที่เลือก)

1. `X-User` หายหรือไม่รู้จัก → **401** (โจทย์ไม่ได้กำหนดรหัส)
2. "เรียงใหม่ไปเก่า" = เรียงตามเวลาสร้างจากมากไปน้อย ถ้าเวลาเท่ากันเรียงตาม id จากมากไปน้อย
3. ผู้จ่ายไม่จำเป็นต้องอยู่ในรายชื่อที่แบ่ง (เช่น alice จ่ายให้ bob กับ carol เท่านั้น) แต่ต้องเป็นสมาชิกกลุ่ม
4. ในการแบ่งแบบ exact ส่วนแบ่งของแต่ละคนต้องมากกว่า 0 สมาชิกที่ไม่มีส่วนแบ่งก็ไม่ต้องใส่ในรายการ
5. จำนวนเงินสูงสุดคือ 9,999,999,999.99 ตามขีดจำกัดของ `NUMERIC(12,2)`
6. คำอธิบายค่าใช้จ่ายต้องไม่ว่างและยาวไม่เกิน 255 ตัวอักษร
7. ลบค่าใช้จ่ายที่ถูกลบไปแล้วซ้ำ → 404
8. `Idempotency-Key` เป็นตัวเลือก ถ้าไม่ส่งมา คำขอแต่ละครั้งสร้างรายการใหม่เสมอ
9. frontend ไม่มี endpoint ให้ดึงรายชื่อผู้ใช้ จึงกำหนดผู้ใช้ 4 คนที่ seed ไว้ตายตัวใน `api.ts`

## ข้อจำกัดที่ทราบและขั้นตอนถัดไป

**ข้อจำกัด**

- ไม่มีระบบยืนยันตัวตนจริง ใครก็ใส่ `X-User` เป็นใครก็ได้ (ตามขอบเขตของโจทย์)
- Idempotency: ถ้าส่ง key เดิมด้วยเนื้อหาคนละแบบ ระบบคืนรายการแรกโดยไม่แจ้งว่าเนื้อหาไม่ตรง
  และ key ไม่มีวันหมดอายุ นอกจากนี้ถ้ารายการนั้นถูกลบไปแล้ว การส่ง key เดิมซ้ำจะได้รายการที่ลบแล้วกลับมา
- เทสต์ backend ต้องมี PostgreSQL จริงและล้างฐานข้อมูลทดสอบทุกครั้ง ยังไม่มี CI
- เทสต์ frontend ครอบคลุมตรรกะ (เงิน การแบ่ง ข้อความ error) แต่ยังไม่มีเทสต์ของหน้าจอ (component/E2E)
- ยังไม่มี pagination ของรายการค่าใช้จ่าย
- ทดสอบบน Windows เท่านั้น (ยังไม่ได้ลองบน macOS/Linux)
- ส่วนเสริมที่ยังไม่ได้ทำ: `settle-up`, `payments` และ Docker Compose

**ขั้นตอนถัดไปที่เสนอ**

1. `GET /groups/{id}/settle-up` คำนวณชุดการจ่ายเงินขั้นต่ำ (จับคู่ลูกหนี้/เจ้าหนี้แบบ greedy ด้วยจำนวนเต็มสตางค์)
2. `POST /groups/{id}/payments` บันทึกการชำระคืนและรวมเข้ายอดคงเหลือ
3. Docker Compose สำหรับ API + PostgreSQL ให้เริ่มด้วยคำสั่งเดียว
4. ตรวจเนื้อหาของคำขอที่ใช้ `Idempotency-Key` ซ้ำ (ตอบ 422 ถ้าไม่ตรง) และกำหนดอายุของ key
5. GitHub Actions รัน `pytest`, `ruff`, `npm test`, `npm run lint` ทุกครั้งที่ push
